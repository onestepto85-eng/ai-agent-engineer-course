  1. Недели 1–6: Python, функции, словари, условия, циклы, исключения, файлы и тесты.
  2. 7–10: HTTP, JSON, API моделей, контекст, структурированные ответы и адаптеры.
  3. 11–15: агентный цикл без фреймворка, инструменты, права, валидация, лимиты. Проект 1.
  4. 16–20: документы, поиск, RAG, источники, память и управление контекстом.
  5. 21–26: графы процессов, подтверждения, сохранение состояния, восстановление и идемпотентность. Проект 2.
  6. 27–30: локальные модели, внешние API, сравнение качества и гибридная приватность.
  7. 31–35: MCP, интеграции, делегирование и проверка необходимости нескольких агентов.
  8. 36–40: evals, трассировка, безопасность, контейнеры, CI/CD, мониторинг и откат.
  9. 41–48: выбор проблемы, исследование пользователей, выпускной сервис, стоимость успешной задачи и портфолио. Проект 3.

Продолжение: обучающие данные, train/validation/test, переобучение, минимальная математика и LoRA/PEFT. Требования к GPU и расходы определяются отдельно.

Урок 1. Модель — не вся система

Пользователь спрашивает: «Где заказ 1042?» Актуальные данные находятся в системе заказов. Модель может предложить вызов инструмента, но приложение должно проверить аргументы и права, выполнить разрешённую операцию и вернуть результат.

  • Модель генерирует ответ или предложение следующего действия.
  • Инструмент — функция с аргументами и результатом.
  • Контроллер управляет выполнением и ограничениями.
  • Состояние содержит данные текущей задачи и результаты шагов.
  • Агентный цикл повторяет выбор действия и обработку результата до остановки.

Корректный номер заказа не означает право читать этот заказ. Проверку доступа выполняет приложение, а не обещание в промпте.

Когда агент не нужен

Для фиксированного сценария проверки статуса можно напрямую вызвать API после проверки прав. В каждом проекте будем сравнивать агентное решение с более простым процессом.

Локальная и внешняя модель

Архитектура предусматривает адаптер модели. При замене заново проверяем форматы ответов, работу с инструментами, качество, скорость и потребление памяти. Одинаковое поведение на любых моделях не обещается.

    Это учебный инструмент без LLM. user_id в реальном приложении нужно получать из проверенной сессии, а не доверять произвольному значению клиента.
    orders = {1042: {"owner": "alice", "status": "shipped"}}

def get_order_status(order_id, user_id):
    if type(order_id) is not int:
        return {"error": "invalid_order_id"}
    order = orders.get(order_id)
    if order is None or order["owner"] != user_id:
        return {"error": "not_available"}
    return {"status": order["status"]}

assert get_order_status(1042, "alice")["status"] == "shipped"
assert get_order_status(1042, "bob")["error"] == "not_available"

    Критерии понимания
    Ты отличаешь модель от контроллера, инструмент от результата и формат аргумента от права доступа. При запрете чтение заказа не выполняется. Ты можешь объяснить функцию без подсказки AI.
